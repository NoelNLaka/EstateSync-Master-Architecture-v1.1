Architecture reference · v1.1

EstateSync — Master SaaS Architecture

A multi-tenant property-management platform with PostgreSQL RLS as its authoritative authorization boundary, and a Cloudflare security edge designed to sit in front of it. Cloudflare would decide whether traffic should reach the application; Supabase Auth decides who the user is; RLS decides which rows they may touch. The fifteen diagrams below trace what that separation implies.

The RLS layer is live. The Cloudflare edge is not yet deployed — it is the target state described by documents 15–21, whose rollout checklist has not been recorded as completed.

02 The core architectural statement

The paragraph everything else in the document set follows from.

EstateSync is a multi-tenant, full-stack SaaS platform in which PostgreSQL is the authoritative data and authorization layer. Web and mobile clients use authenticated Supabase sessions; PostgREST exposes the database through the schema; RLS enforces tenant isolation; Edge Functions handle narrowly scoped privileged operations; integrations are isolated behind explicit boundaries; and CI/CD continuously tests database security and tenant isolation.

The architecture is designed to scale from a single organization to a multi-organization SaaS while preserving a clear security boundary and auditable business operations.

Added in v1.1 as a design, not as a deployed control. A Cloudflare security edge is specified to sit in front of the public surface; as of 2026-09-18 it is not in place, and a request to the application’s hostname is answered directly by Vercel. Cloudflare is the intended perimeter layer; PostgreSQL RLS is today the authoritative multi-tenant authorization boundary and the only one actually enforcing. The designed control chain runs Internet → Cloudflare → Vercel / Supabase → Supabase Auth → application authorization → PostgreSQL RLS → database constraints → audit and monitoring; today it runs without the second hop.

03 The security edge

Three different layers, three different questions. This separation is mandatory.

Cloudflare should answer “should this traffic reach the application?”. Supabase Auth answers “who is this user?”. PostgreSQL RLS answers “can this user access this row?”. Each is useless as a substitute for the others, and the failure mode of every perimeter product is the assumption that it also does authorization.

LayerResponsibility
CloudflarePerimeter, DDoS, WAF, rate limits, bot and challenge controls
VercelWeb hosting, build and deployment
Supabase AuthIdentity, sessions, JWT
ApplicationBusiness authorization and validation
PostgreSQL RLSTenant and row authorization
DatabaseIntegrity constraints
Audit / monitoringAccountability and detection
What the edge cannot do

A rate limit can slow an abusive client; it cannot decide whether that client is entitled to a given tenant’s rows. Perimeter controls are probabilistic and tuned against real traffic, identity is a claim about a session rather than an entitlement to data, and only RLS sees the row being requested.

04 Trust boundaries

Traffic crosses four times, and trust is granted only once — at the row, by RLS.

BoundaryCrossingEnforced by
TB-01Internet → CloudflareWAF, DDoS protection, rate limits, bot controls
TB-02Cloudflare → Vercel / SupabaseOrigin configuration and TLS
TB-03Service zone → PostgresJWT → org membership → RLS → row access
TB-04Postgres → external integrationsIntegration adapters, idempotency, webhook verification
Two rules that define the boundary

Service-role credentials are restricted to trusted server-side environments such as Edge Functions, and are never exposed to web or mobile clients.

AI coding agents are outside the production trust boundary and receive least-privilege development credentials only. An agent may change the architecture; it may not hold a credential that reaches production data.

A perimeter control is not a business control

Rate limiting is a perimeter control, not a precise business counter. Application authorization, idempotency and financial controls remain inside EstateSync — the edge decides whether traffic arrives, not what it is allowed to do.

06 Deployment topology

Both shapes are supported; the choice is per-API, not per-project.

OptionPathUse when
A — initialBrowser → Cloudflare → Vercel, Supabase via the Supabase clientDefault. The perimeter protects the public application and RLS protects direct Supabase access.
B — controlled gatewayBrowser → Cloudflare → Worker / API gateway → SupabaseSelectively, for sensitive APIs or integrations where centralised edge controls justify the added complexity.

DNS surfaces are part of the security posture, not just routing:

  • app.example.com → Vercel
  • www.example.com → Vercel
  • staging.example.com → staging environment
  • admin.example.com → protected administrative surface

Mobile clients use Supabase Auth and the normal Supabase client pattern; PostgreSQL RLS remains their tenant-isolation boundary. There is no Vercel application in that path.

Do not over-proxy. Do not proxy every CRUD operation without a concrete requirement, and do not expose internal infrastructure merely for convenience — every added hop is a new place for authorization assumptions to hide.

07 Zero Trust & internal access

Cloudflare Access in front of everything that should never have been public in the first place.

An internal resource is reachable only after identity → MFA → device policy → access policy have each narrowed who can continue. Public customer traffic and internal administration are governed by separate policies on purpose: sharing one policy across both populations means the weaker requirement silently sets the bar for the stronger one.

Candidate protected resources:

  • staging environments
  • internal admin portal
  • monitoring dashboards
  • deployment tools
  • AI software-factory control plane
  • development services
  • database administration interfaces
Not a substitute

Zero Trust protects reachability of internal tools. It is not a replacement for PostgreSQL RLS: an authenticated developer reaching staging still meets RLS on every row, and a compromised internal session still cannot read another tenant’s data.

08 Runtime shape

There is no application server. There is one privileged path.

The request path is short by design: a client holding the publishable key and an authenticated JWT reaches Auth / GoTrue, then PostgREST, then PostgreSQL — where the authentication context, RLS policies, grants and business constraints are all applied in the database rather than in a service tier that could be bypassed or forgotten.

The privileged path exists for the work that cannot be done that way. An Edge Function validates the JWT, the role and the input, derives the organization context, and only then performs the privileged operation under service_role.

Anything long-running or externally dependent — email, SMS, PDF and report generation, payment reconciliation, scheduled rent reminders, outbound webhooks — belongs behind an event or queue boundary rather than in the request.

The one rule with no exceptions

The service role must never be exposed through a VITE_* or EXPO_PUBLIC_* variable. Every other decision in the runtime architecture is downstream of that — including the v1.1 rule that the credential lives only in trusted server-side environments such as Edge Functions.

09 Tenant isolation

The load-bearing mechanism — which is why authorization is written in SQL.

Membership lives in org_members, deliberately not on profiles, so a user cannot change their own tenancy by editing a row they own. Every tenant-owned table then carries a stored organization_id.

Because tenancy is a stored column rather than something derived by joining up through a property to a landlord, one predicate covers every table — adding a domain is a migration, not an authorization redesign. The row set is decided inside Postgres after the query arrives, so a UI filter bug, a forged client and a raw curl with the public key all land on the same gate. This is also why the Cloudflare edge cannot be the authorization boundary: it never sees the row.

The architecture plans to move from user → one organization to a user with several organizations, where the active organization is request or session scoped and explicitly selected rather than inferred with LIMIT 1.

The mandatory tenant-table contract

A tenant-owned table is not complete until it has all seven of these. The grants are the one people forget, and their absence produces 42501 permission denied even with perfect policies.

  1. organization_id
  2. row level security enabled
  3. row level security forced where appropriate
  4. correct policies
  5. correct grants
  6. appropriate indexes
  7. audit behaviour where required

13 Delivery & operations

Half of the required gates interrogate the schema rather than the application code.

Pull requests pass through lint and typecheck, unit tests, a build, migration validation, secret scanning, a dependency audit, edge-function authorization, workflow hardening, RLS coverage and tenant isolation before anything reaches staging. The last two are properties of the database, not of the code: rls-coverage asserts every tenant-owned public table has RLS enabled, a policy, the required grants and the tenancy column; tenant-isolation plants rows for two organizations and proves under RLS that neither can read the other’s, then rolls the transaction back.

Dependency scanning was added on 2026-09-18, closing a gap this page had been asserting was already closed. It blocks on critical rather than high, deliberately: every current high is Expo’s build toolchain, none of it ships inside the APK and none is fixable without breaking the build, and a gate that is red from the day it lands over findings nobody can act on gets ignored — after which its red hides a real one. Highs are recorded rather than swallowed.

Still not implemented, and listed so the gaps stay visible: integration testing is partial, automated code review is configured but dormant, and there is no periodic review of org membership, roles or token scopes.

Migrations are forward-only and production migration is automated and auditable. Secrets live in the platform secret manager, and token-based deployment means ordinary CI needs no database password. A failed deployment has to be observable and reversible.

Outside the pull-request path, on a schedule: nightly encrypted backups, weekly restore drills that prove the backup is recoverable rather than merely produced, daily security-posture monitoring, and staging error monitoring every six hours. Monitoring covers application and database errors, authentication failures, Edge Function failures, payment and webhook failures, storage failures, abnormal authorization failures, and backup or restore-test failures. The dependency audit also runs daily at 05:00. Periodic access review is not implemented.

One failure mode is worth recording because it shaped the monitoring design. Between 5 and 18 September 2026 the nightly backup failed every night: the dump and the encryption succeeded and only the artifact upload failed, because a storage quota shared account-wide with unrelated builds was full. Every step the job could report on looked healthy, so nothing raised it for fourteen nights. The posture monitor now checks for the backup artifact itself — a control whose output stops appearing has to be detected by its output, not by the exit status of the job meant to produce it.

audit_logs captures organization, table, record, action, previous and new value, actor, timestamp and request identifier where appropriate. Recovery objectives — RPO, RTO, retention, restore frequency, ownership and escalation — are explicit project decisions rather than assumptions.

14 Cloudflare rollout checklist

Five phases, each a gate on the next. Each phase is a precondition, not a one-off task.

Phase 1 — Baseline

  • Move authoritative DNS to Cloudflare
  • Enable HTTPS / TLS
  • Enable managed WAF baseline
  • Review Security Events
  • Configure security headers
  • Confirm Vercel / Supabase origins and domains

Phase 2 — Abuse controls

  • Rate-limit login
  • Rate-limit signup
  • Rate-limit password reset
  • Rate-limit public forms
  • Protect document / file operations
  • Protect payment initiation
  • Protect webhooks

Phase 3 — Turnstile

  • Separate development, staging and production widgets
  • Add Turnstile to signup
  • Add Turnstile to password reset
  • Add adaptive protection to login
  • Validate every token server-side
  • Keep the secret key server-side only

Phase 4 — Advanced controls

  • Add custom WAF rules
  • Add bot / challenge policies
  • Protect admin paths
  • Add Cloudflare Access for internal tools
  • Add Worker gateway only where justified
  • Review false positives periodically

Phase 5 — Security tests

  • Credential stuffing
  • Signup automation
  • API bursts
  • Document enumeration
  • Cross-tenant IDs
  • Malicious payloads
  • Forged webhooks
  • Unauthorized admin access

The three constraints that decide a free rollout
  1. One rate-limiting rule — path-only expression, per-IP counting, 10-second window and mitigation. Every threshold in doc 17 is outside what Free can express.
  2. The Free Managed Ruleset is the only managed ruleset — the Cloudflare Managed and OWASP Core rulesets are Pro and above.
  3. No log action — there is no dry-run, so a rule acts immediately and has to start narrow, widening from Security Analytics.

The gap that is not about money. In Option A the edge only ever sees the Vercel-served hostname: supabase-js talks to the project hostname directly, so the API and data surfaces in the doc 17 matrix are unreachable by the perimeter on any plan. Option B — a Worker gateway, 100,000 requests/day on Free — is what brings them back. Doc 17's paths also do not match Supabase's real endpoints (/auth/v1/token, /rest/v1/*, /storage/v1/*, /functions/v1/*), so the matrix needs a mapping pass before implementation.

Operating Free. Move the other six rate-limit surfaces into the application as counters — a Durable Object on the free SQLite backend is precise, not approximate — and lead with Turnstile plus leaked-credential detection, which are both free and are the right controls for authentication anyway. Verify Bot Fight Mode against mobile clients and provider webhooks before leaving it on: it is domain-wide and cannot be selectively skipped. Full detail, sources and the phase-by-phase adaptation are in 21-cloudflare-free-plan-feasibility.md.

What no plan changes. Cloudflare answers whether traffic should reach the application; Supabase Auth answers who the user is; PostgreSQL RLS answers whether that user may access that row. A free-tier deployment loses perimeter breadth, not the boundary — every request that reaches Postgres still meets the gate that decides tenant access.

17 Architecture as an engineering contract

The document set is written to be a guardrail for AI-assisted development, not only a diagram for humans.

Source-of-truth hierarchy. Where two sources disagree, the higher one wins.

  1. architecture contract
  2. database schema and migrations
  3. RLS and authorization policies
  4. application code
  5. automated tests
  6. deployment

Rules for an AI coding agent working in this repository.

  1. read the architecture before changing code
  2. never weaken RLS to solve a UI problem
  3. never expose service-role credentials
  4. never modify a merged migration in place
  5. add tenant-isolation tests for new tenant domains
  6. update the architecture when introducing a new domain
  7. update security documentation when changing trust boundaries
  8. use least privilege — agents hold development credentials only
  9. preserve auditability

The change workflow. A request moves through architecture impact analysis, schema / API / security design, implementation, automated tests, tenant-isolation tests, security checks, staging, approval, production, and finally an architecture update — so the document set cannot silently drift from the system it describes.
